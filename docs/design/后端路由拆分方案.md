## 四、必须先说清的三个风险

### 1. 路由顺序是有语义的（`student.py`）

`student.py` 里 `/articles/page` 注册在 `/articles/{article_id}` **之前**（1043 vs 1064）。FastAPI 按注册顺序匹配，若拆分后两个模块注册顺序颠倒，`/articles/page` 会被 `{article_id}` 吃掉，返回 422（`page` 不是整数）。

**已实测证明**（不是推断）：用同样两个路由构造一个「通配在前」的临时 app，`GET /api/student/articles/page` 返回 **422**：

```
{'detail': [{'type': 'int_parsing', 'loc': ['path', 'article_id'],
             'msg': 'Input should be a valid integer, unable to parse string as an integer',
             'input': 'page'}]}
```

也就是说这个顺序依赖一旦被拆错，**不是 404、是 422**，症状看起来像参数校验 bug，很难第一时间联想到注册顺序。这是本次拆分最需要守住的一条。

**同类顺序依赖：经实测是两处，student 与 teacher 各一处。**

| 位置 | 字面路由 | 通配路由 | 行号 |
|---|---|---|---|
| `student.py` | `/articles/page`（18） | `/articles/{article_id}`（20） | 1043 / 1064 |
| `teacher.py` | `/articles/page`（21） | `/articles/{article_id}`（23） | 1207 / 1227 |

括号里是 `router.routes` 里的实际注册下标（0 起），两侧都是「字面在前、通配在后」。

我最初把 `/questions`（POST）与 `/questions/ask`（POST）、`/treehole/posts`（GET）与 `/treehole/{post_id}/comments`（GET）也列为顺序依赖，逐条核对真实路由表后**这两条都不成立**：

- `/questions` 与 `/questions/ask` 都是字面路径，没有通配段，注册顺序不影响匹配
- `/treehole/posts` 是 3 段、`/treehole/{post_id}/comments` 是 4 段，段数不同，前者不可能吃掉后者

所以拆分时**必须保住的是两处 `/articles/page` 先于 `/articles/{article_id}`**。这条纠正本身值得记：凭「长得像」推断顺序依赖会虚报风险，而只核一侧会漏掉另一侧——第一版我写了三处（两处假），第二版只写了 student 一处（漏了 teacher），两版都错。**必须对着 `router.routes` 的实际下标逐侧核。**

### 2. `teacher.py` 与 `advanced_teacher.py` 前缀不同

`teacher.router` 自带 `prefix="/api/teacher"`，`advanced_teacher.router` **无前缀**。拆分 `teacher.py` 时，新模块必须继承同样的 prefix，否则路由整体漂移。

### 3. 六组同名接口不是重复实现

`/articles`、`/articles/page`、`/articles/{id}`、`/appointments`、`/questions`、`/dashboard/stats` 在 student 与 teacher 两侧同名，但**前缀不同**（`/api/student` vs `/api/teacher`），且 ACL 与返回契约不同（teacher 侧带学生归属过滤）。**拆分不是合并**，不能顺手去重。

**而且连 HTTP 方法集都不同**，这是「不是重复实现」最硬的证据（实测同路径去前缀后的方法集合）：

| 路径 | student | teacher |
|---|---|---|
| `/appointments` | `GET` + `POST` | `GET` |
| `/articles` | `GET` | `GET` + `POST` |
| `/articles/{article_id}` | `GET` | `GET` + `DELETE` |
| `/articles/page` | `GET` | `GET` |
| `/dashboard/stats` | `GET` | `GET` |
| `/questions` | `GET` + `POST` | `GET` |

口径要说清，否则「几条重复」会算成三个数：**完整方法集相同的有 2 组**（`/articles/page`、`/dashboard/stats`），**只要共有 `GET` 就相同的有 6 组**（六条路径两侧都有 GET）。我最初写的「3 条同路径同方法」是错的：`/questions` 两侧方法集是 `GET+POST` 对 `GET`，方法集并不相同，只是共有 GET。

所以「六组重复接口」这个说法是粗的：**真正同形状（方法集也相同）的只有 2 条**，另 4 条方法集不同，天然不会混淆。

## 五、建议的落地顺序（分批，每批可独立回滚）

**第 1 批（最低风险）**：拆 `student.py` → `student_dashboard.py` + `student_report.py`（13 条路由，无顺序依赖）。

**注意这一批不是「纯读」**：`student_report.py` 里的 `POST /tests/submit`（`student.py:476`）会 `db.add(TestResult)` + `db.commit()`，还会失效报告缓存（`_invalidate_user_report_cache`）。我最初把它写成「纯读接口、无写库」是错的。选它当第 1 批的理由因此改成：**它没有顺序依赖、也没有跨模块共享的私有函数**，而不是「没有写库」。回归时必须覆盖一次提交写入。

**第 2 批**：拆 `student.py` → `student_treehole.py`（7 条，含写接口，但顺序依赖集中在组内，一起搬即可）。

**第 3 批**：拆 `teacher.py` → `teacher_crisis.py` + `teacher_media.py`（11 条）。

**第 4 批**：`advanced_chat.py` 1475 行单独评估——它的 10 条路由平均 147 行，拆模块收益低于**拆函数**，建议先做函数级拆分，不改路由。

**每批的验收口径**：
1. `git diff -M` 只含移动、不含逻辑改动
2. 基线仍是 228 passed / 3 skipped
3. 门禁 `real=0 lazy=0` exit 0
4. **`dump-route-table.py --check` exit 0**：这是最硬的等价性证据，连注册顺序一起比
5. 顺序依赖的两处 `/articles/page` 单独回归（student + teacher）
6. 拆分涉及写接口时（如第 1 批的 `POST /tests/submit`），回归要覆盖一次真实写入

## 六、路由快照门禁

**已经落地**（`31e3ea2` + 本批），不需要等测试配合：

- `backend/scripts/route-baseline.json`：**100 个 path+method 对**（99 个 HTTP + 1 个 WebSocket），按真实注册顺序
- `backend/scripts/dump-route-table.py --check`：比对**活的**路由表与基线，任何漂移 exit 1

```powershell
.\.venv\Scripts\python.exe backend/scripts/dump-route-table.py --check
```

**范围是「已挂载的整个 app」，不是单个 router 文件。** 这一点我最初写错了，外脑指出后实测确认：第一版只遍历各 router 模块自己的 `.routes`，结果
- 漏掉 `include_router` 的挂载前缀：`advanced_chat` 实际在 `/api/advanced-ai` 下，快照却记成裸路径，该模块 **10 对**全部记错（我一度写成「18 条」，那是 `app.routes` 的条目数，不是该模块的路由数）；
- 漏掉两个 `@app` 根端点：`/` 和 `/api/v1/model/current`；
- 报 98 对，而真实 app 的 HTTP 路由是 **99 对**。

现在路径与前缀取自挂载后的 app，**顺序**取自真实路由对象（FastAPI 0.140 把 `include_router` 存成惰性 `_IncludedRouter`，`openapi()` 有路径没顺序、`app.routes` 有顺序没路径，所以两边都要走）。脚本会**交叉校验**重建结果与 `app.openapi()` 的 path+method 集合完全相等，不一致直接 exit 1——这是防止它自己算错的自检。

**WebSocket 单独覆盖**（外脑第二次复核发现的缺口）：`app.openapi()` 只描述 HTTP，`APIWebSocketRoute` 也没有 `methods` 属性，所以上一版把「整个 app」说大了——`/api/ws` 根本不在快照里。外脑在隔离进程里移除真实的 WS 挂载后，`--check` 仍报 `IDENTICAL 99`、exit 0。现在 WS 以 `method: "WS"` 记入快照（order 95），并且**用一条独立的计数路径**（只数、不走有序遍历）交叉验证，两个数字不等就 exit 1；实测把有序遍历改成看不见 WS 时，`collect()` 报 `walk found 0, independent count found 1` 而不是静默返回 99。移除 WS 挂载后 `--check` 变成 `DIFFERENT: left=100 right=99`、exit 1。

**导入失败是致命的**：上一版把模块导入异常记成一条数据，导致 `--json` 仍 exit 0，`compare()` 还会 `KeyError` 崩掉。现在任何导入/取 spec 失败都 exit 1，不会出现「代码坏了、门禁绿了」。

**它比「集合相等」严格**：连注册顺序一起比。实测把 `/api/student/articles/page`(21) 与 `/api/student/articles/{article_id}`(23) 对调（集合完全不变），`--check` 报 `SET IDENTICAL BUT ORDER CHANGED` 并 **exit 1**；恢复后 exit 0。

拆完一批后如果路由**是有意改变**的，用 `--save` 重新生成基线，那个 diff 就是评审物件。
