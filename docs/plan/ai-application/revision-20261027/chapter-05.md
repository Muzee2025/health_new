## 5.1 从记录到可读摘要

项目已有Vue前端、FastAPI服务和SQLite数据存储，测评提交、对话记录、报告查看及教师端个体材料等入口已经形成。下一步不是让模型直接“判断学生”，而是把已有记录整理成教师能核对、学生能理解的材料：先确认数据说了什么，再用检索和生成帮助组织文字，最后由教师结合实际情况决定是否答复或跟进。

一条记录进入分析前，系统应检查来源、时间、字段是否齐全、取值是否在允许范围，以及记录间能否比较。例如量表名称或版本不同，就分开呈现；缺少某次记录时明确显示缺失，不用估算值补齐。教师查看个人材料时，可以看到所选时间范围、纳入记录数和未纳入原因。面向群体的图表则先说明统计口径和样本数，避免把记录条数误当成独立人数。现有基础统计可展示分布和一段时间内的变化；只有数据口径相同、时间点足够时，才适合谈趋势。结果是对现有记录的描述，不是诊断或风险裁定。

## 5.2 规则、检索与大模型各做什么

分析分成三步。第一步由规则和统计代码整理字段、计数、时间序列及变化值。这些结果应能从对应记录复算，图表旁标出数据期间、记录数和缺失情况。规则适合做一致的格式检查和汇总，不应把固定关键词分数包装成专业结论。第二步由知识检索从经确认的校内资料或服务说明中寻找相关段落，提供给摘要起草任务。找不到合适资料时，应说明依据不足，不让模型自行补出制度、联系方式或服务承诺。第三步才由大模型把已确认事实和检索材料写成短摘要草稿；摘要应把“记录显示”“尚缺信息”和“需要教师核对的问题”分开，附上所用时间范围及资料出处。

例如一份摘要可以按以下字段组织，而不是输出一个笼统标签：

| 摘要部分 | 展示内容 |
| --- | --- |
| 已有记录 | 选定期间内的测评或留言记录及其时间；数值只按同版本、同口径比较 |
| 尚缺信息 | 未填写字段、缺少的时间点或无法比较的版本 |
| 待核对问题 | 对记录含义仍不确定之处，以及建议教师向学生确认的事实 |
| 参考依据 | 使用的校内说明或服务资料名称、版本及对应段落 |

这里的字段是建议的摘要结构，不代表已经形成经过评测的生成格式。教师端应同时显示原始记录入口与摘要草稿，允许教师逐项核对、更正或弃用；只有经人工确认的文字才进入后续沟通。AI负责把材料整理得更容易读，教师负责理解语境、选择是否联系学生以及如何回应。学生可以通过现有求助入口发起沟通；收到的答复由教师核实后发送，不能由模型自动发送或触发处置。

## 5.3 生成不可用时仍能继续服务

模型或检索不可用不应遮住已保存的测评、留言和求助记录。页面应把状态说清楚，例如“摘要暂不可生成”，同时保留记录查看、补充信息和发起求助的入口。教师仍可直接查看原始材料并人工答复；系统不得把本地规则结果伪装成大模型生成内容。这样，生成能力是整理材料的一种辅助方式，而不是学生获得人工支持的前置条件。

现有基础与后续建设分开说明：

| 已有工程基础 | 拟建设与验证 |
| --- | --- |
| Vue、FastAPI、SQLite；测评、对话、报告及教师材料页面；局部统计、可选RAG与模型接口 | 统一字段质量检查和比较口径；摘要分栏展示事实、缺失与问题；教师核对后使用；完善生成失败时的记录与求助体验 |

后续应先用合成记录检查缺失、版本不一致、无检索结果、超时和人工更正等情形，再由业务及专业人员确认摘要字段和资料范围。只有在数据使用、模型服务及评审安排获批后，才开展隔离评测。项目当前没有真实模型效果结论；工程界面和接口存在，也不能替代对输出质量的验证。人员、导师、周期与经费由负责人后期填写。
