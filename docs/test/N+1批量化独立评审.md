## 二、问题 1：批量 `IN` 撞变量上限（新引入回归）

### 2.1 机制

`SQLITE_LIMIT_VARIABLE_NUMBER` 在本机（SQLite 3.53.1）实测 **32766**。
旧实现逐行查询，每次只绑几个变量，**任何规模都不触发**；
新实现把整批 id 塞进一个 `IN (...)`，**规模一到就崩**。

### 2.2 我测到的阈值（固定提交上测，代码不会中途变）

用固定 worktree 在 `87a7ef7`（修复前）上测，每个规模新建库并断言真实行数：

| 端点 | 崩溃阈值 | 崩溃时单语句绑定参数 |
|---|---|---|
| `teacher/questions` | **32766 行** | 32769 |
| `student/questions` | **32766 行** | 32769 |
| `crisis/pending` | **>32766 条不同消息 id**（32766 通过，33000 崩） | = id 数 |

**对照组**：旧实现在 40000 行下**正常返回 40000 条**。
所以这是新引入的回归，不是既有上限。

### 2.3 我自己的测量错误（记录，避免被误用）

我先后给后端报过不一致的数字，原因是**测量基线在漂**：后端边改边写工作区，
我 19:5x 的探针跑的是改前代码，20:0x 的跑的是改后代码。不是阈值难测。

另外两个我自己的缺陷，一并记录：
- 一次监听绑到了 `app.database.engine`，而 session 用的是新建 engine，捕获为空却照常输出数字
- 一次二分搜索的变量根本没改变种子规模，返回了假的「1000」

**结论：这类阈值必须钉在固定提交上测，并且断言捕获非空。** 后续任何人复测请照此做。

### 2.4 修复验证

`be6e6f7` 把物化 `IN` 列表换成 JOIN / 子查询。我在修复后代码上复测：

| 端点 | 40000 行 |
|---|---|
| `teacher/questions` | **OK**（40000 行） |
| `teacher/interventions` | **OK**（40000 行） |
| `crisis/pending` | 修复路径已换 JOIN |

等价性**没有退化**：修复后重跑 `review-n1-batch2.py` / `batch3.py`，
仍然全部 EQUAL、`FAILURES: none`。

## 三、问题 2：`teacher/students` 漏修（未修，需跟进）

`be6e6f7` 的提交信息列了 5 个端点，**不含 `teacher/students`**，但它有同样的缺陷。

`backend/app/routers/teacher.py`：
- `:889` `models.TestResult.user_id.in_(student_ids)`
- `:905` `models.StudentProfile.user_id.in_(student_ids)`
- `:916` `models.CrisisWarning.student_id.in_(student_ids)`

实测（修复后的 `be6e6f7` 上）：**33000 个学生的名单直接抛
`OperationalError: too many SQL variables`**，而旧实现能跑完。

这是同一根因的漏网，属 `6ef94ea` 引入。**建议与问题 1 一并修**，
把 `student_ids` 同样换成子查询/JOIN。

### 还有若干未改的物化 `IN`

同一批代码里仍有多处 `in_(python 列表)`，例如
`teacher.py:831/835/1137/1257/1261`、`student.py:283/287/293/376/380`。
它们大多以「教师数」「会话数」为规模，现实中到不了 3 万，
**我不把它们列为缺陷**，但建议作者自查一遍哪些会随用户数据无界增长。

## 四、问题 3：作者探针的 NULL 用例不可能出现（论证瑕疵）

`884a72b` 提交信息说种子覆盖了「message content 为 NULL」，
并称早稿把 None 归一成 `""` 被探针抓到。

但 `backend/app/models.py:405`：`content = Column(Text, nullable=False)`。
**NULL 内容在这个 schema 下写不进去**（我构造时被 `NOT NULL constraint failed` 挡住）。
所以那个用例实际测的是空字符串，不是 NULL。

不影响正确性（空串路径已验证一致），但**这条覆盖是虚的**，
不应作为「NULL 分支已验证」的依据。

## 五、我确认没问题的地方（明确说对在哪）

- `student/appointments` 的 `"未知"` 兜底：profile 缺失与 location 为 NULL 是**两条不同路径**，新旧都正确区分
- `teacher/students` 的 `has_pending_crisis = count > 0`：`GROUP BY` 只对有 pending 的学生出行，缺失走 `(0, None)` 默认值，等价
- `row_number()` 分区取最新：同时间戳时按 `id desc` 兜底，与旧 `ORDER BY created_at desc` + 首行在**同秒多行**场景下的行为一致（已用共享时间戳种子验证）
- 权限边界未放宽：`assigned_student_ids` / `assigned_teacher_ids` 的过滤条件在批量化后原样保留，我构造的越权种子没有多看到任何行
