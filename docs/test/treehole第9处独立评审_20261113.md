## P2：收藏子查询重复求值，导致已加载帖子的计数丢失

**位置（均按 d1e6bf0）：**

- [student.py:1274](../../backend/app/routers/student.py#L1274) 将筛选条件保留为查询；第 1275 行先执行 `posts = query.all()`，固定本次响应的帖子列表。
- [student.py:1216](../../backend/app/routers/student.py#L1216) 创建子查询；随后五次互动查询在第 1218/1221/1224/1229/1232 行各自重新执行该查询。
- [student.py:1260](../../backend/app/routers/student.py#L1260) 的 `favorites` 分支依赖当前收藏记录，集合可在上述查询之间改变。
- [student.py:1245](../../backend/app/routers/student.py#L1245) 对未查到的记录填 0，第 1248 行对未查到的点赞填 False，最终仍按先前加载的 `posts` 返回该帖。

**可达触发顺序：**

1. 用户 A 已收藏帖子 P；P 有 2 个点赞、2 条评论、2 条收藏，A 自己点过赞。
2. 请求 `GET /api/student/treehole/posts?tab=favorites` 已执行完帖子列表 SELECT。
3. 另一连接取消 A 对 P 的收藏并提交；这是现有 [toggle_favorite](../../backend/app/routers/student.py#L1301) 的正常删除及提交行为。B 的收藏仍在，点赞和评论没有改动。
4. 原请求继续读取互动信息。新版五次子查询都重新筛选 A 的收藏，P 已不在集合中，因此漏掉 P 的全部互动信息。

| 响应字段 | 原逐帖版 46b0103 | 物化列表版 e7a0be8 | 新子查询版 d1e6bf0 |
| --- | --- | --- | --- |
| `likes_count` | 2 | 2 | **0** |
| `comments_count` | 2 | 2 | **0** |
| `favorites_count` | 1 | 1 | **0** |
| `is_liked` | true | true | **false** |
| `is_favorited` | false | false | false |

三个版本均返回 P。新版额外改变了未发生变化的点赞、评论信息；这是对前两版的新增回归。影响是该次响应显示错误计数及点赞状态，没有测到持久化修改或越权泄露。

**独立复现：** 两个独立 SQLite engine 连接同一个全新合成库，在首条互动聚合查询执行前通过第二连接取消收藏并提交。记录此时读连接 `sqlite3.Connection.in_transaction == False`，确认仓库现有默认连接行为没有跨 SELECT 的 SQLite 读取快照。每个版本独立新建库，三个版本执行同样交错；原版与物化版相等，新版的等价性断言失败。

**修复验收要求：** 在消除无界绑定参数、保持查询数不随帖数增长的同时，为一次响应里的帖子与互动信息提供一致的集合语义。至少复跑上面的取消收藏交错用例，确认点赞数、评论数和本人点赞状态不再凭空丢失。是否使用一个查询返回帖子及互动、明确读取事务或其他方式，由后端选择并验证；本报告不修改业务实现。
