### 3.2 Linux 干净树：复现失败

做法：用 `git -c core.autocrlf=false archive` 导出 **HEAD 的 LF 内容**（`git archive` 默认会按 Windows `autocrlf` 转成 CRLF，必须显式关闭），解到 WSL ext4（`/mnt/c` 大小写不敏感，不能用来复现），用 **Node v24.14.0**（与 CI `node-version: 24` 对齐）跑同一脚本：

```
$ node scripts/check-assets.mjs
Asset check: FAILED
Approved: 124; legacy-unverified: 7; coverage: 131/131
ERROR HASH_MISMATCH avatars/psych-teacher-cartoon.svg: Manifest sha256 does not match file content.

```

同一棵树上后续两步：
- `node --test scripts/tests/check-design-sources.test.mjs` → **exit 0，7 pass / 0 fail**
- `node scripts/check-design-sources.mjs` → **exit 0，`"status": "passed"`，0 errors**

即：CI 里只有 `assets:check` 会挂，被 skip 的第 8、9 步在本机 Linux 等价环境下都能过。

### 3.3 失败命令链

`npm run assets:check` → `node scripts/check-assets.mjs`：
- 对 manifest 里每个资产按**原始字节**算 sha256（`scripts/check-assets.mjs:160-162`），与 `item.sha256` 比较，不一致就 `add(errors,'HASH_MISMATCH',...)`；该资产 `status` 是 `legacy-unverified`，但**哈希校验对 legacy 资产同样执行**。
- 有 error 时 `process.exitCode = 1`（`scripts/check-assets.mjs:313`）。

## 4. 根因证据链

出问题的条目（`src/assets/manifest.json`，从 1895 行开始）：

```json
{
  "id": "legacy-psych-teacher-cartoon-svg",
  "path": "avatars/psych-teacher-cartoon.svg",
  ...
  "status": "legacy-unverified",
  "sha256": "fb424040ce5be0cb9e5b67b1d47f2c809aa781563caafd373c6ddaff6dbe6221"   // 第 1908 行
}
```

| 对象 | 字节数 | sha256 | 说明 |
| --- | --- | --- | --- |
| Windows 工作区文件（CRLF） | 2236 | `fb424040…6be6221` | **= manifest 记录值**，所以本机 PASSED |
| Git blob / Linux checkout（LF） | 2198 | `76bde907…038baba` | **≠ manifest**，所以 CI FAILED |

- 两者差 38 字节，正好是 38 个 `\r`（CRLF→LF）。
- `git ls-files --eol src/assets` 里它是全目录**唯一**的 `w/crlf` 条目：

  ```
  i/lf    w/crlf  attr/    src/assets/avatars/psych-teacher-cartoon.svg
  ```

  `attr/` 列为空，说明没有 `.gitattributes` 规则作用于它——仓库里只有两处 `.gitattributes`：`src/assets/icons/phosphor/.gitattributes`（`*.svg -text`）和 `docs/design/ppt-kit/upstream/.gitattributes`，都不在 `avatars/` 路径上。
- 用 git blob 逐条模拟 CI 侧哈希：manifest 共 131 条，**只有这 1 条**在 CI 内容下不一致；其余 130 条都匹配（对应 Linux 复现里只有 1 条 ERROR）。
- 为什么 CI 的 `npm test` / `npm run build` 没拦住：这两步不读 manifest 的 sha256；`assets:source-check` 只校验 catalog 引用的 21 个 approved 资产，该文件是 legacy，不在其中。

一句话：**manifest 是在 Windows CRLF 工作区上生成的哈希，Linux checkout 是 LF，字节不同 → 哈希失配。** 这是典型的「本机过、CI 挂」，与 Lead 本机 `assets:check` exit 0 完全一致。

## 5. 修法

### A. 数据修正（必须）

`src/assets/manifest.json:1908`，改为 **LF 内容哈希**：

```
"sha256": "76bde907d206348d9e4c6447d7db76ecf8838a4f2de75729ed8b26f57038baba"
```

owner：前端（`src/`）。实测：只改这一行后，Linux 干净树 `assets:check` **exit 0 PASSED**。

但**只做 A 不够**：当前 Windows 工作区文件仍是 CRLF，改完本机会变成 exit 1（已实测），所以需要 B 或 C 之一。

### B. 校验脚本按 LF 归一化算哈希（推荐，测试 owner）

让哈希不依赖 checkout 的换行符，`manifest` 存平台无关（LF）哈希。`scripts/check-assets.mjs`：

```js
// 现在
const hashFile = (p) => crypto.createHash('sha256').update(fs.readFileSync(p)).digest('hex');

// 建议（文本资产先做 LF 归一化再哈希）
const TEXT_ASSET = /\.(svg|txt|md|json|css)$/i;
const hashFile = (p) => {
  let buf = fs.readFileSync(p);
  if (TEXT_ASSET.test(p)) buf = Buffer.from(buf.toString('utf8').replace(/\r\n/g, '\n'));
  return crypto.createHash('sha256').update(buf).digest('hex');
};
```

同一归一化建议同步到 `scripts/check-design-sources.mjs:44`（catalog 引用资产的哈希），因为 `hashFile` 也用于 `sourceSha256`（`check-assets.mjs:170`），这样第三方 `sourceInput` 的哈希在 Windows 上也不会因 EOL 漂移。

实测等价性（同一文件两种字节，归一化后哈希相同）：

```
raw crlf           fb424040ce5b…6be6221
raw lf             76bde907d206…038baba
normalized-crlf    76bde907d206…038baba   ← 与 LF 一致
```

效果：A+B 之后，Linux（LF）和 Windows（CRLF 或 LF）都会算成 `76bde907…`，本机和 CI 同时绿，且**不需要重新 checkout**。

### C. 仓库属性防复发（建议一起做，前端/Lead 执行）

新增 `src/assets/.gitattributes`：

```
*.svg  -text
*.png  binary
*.webp binary
*.ico  binary
```

`-text` 表示不做换行转换、checkout 字节与索引逐字节一致，效果比 `text eol=lf` 更硬，和现有 `src/assets/icons/phosphor/.gitattributes`（注释写明 “Preserve downloadable SVG bytes”）的做法一致。
约束以后所有 checkout（含 Windows）都写 LF。注意：仓库里已存在的 CRLF 工作区文件不会自动重写，需要 `git checkout-index -f -- src/assets/avatars/psych-teacher-cartoon.svg` 刷新一次（Git 操作由 Lead 执行）。若已做 B，则 C 只是保险，不是必须。

### 不推荐

- 把 manifest 哈希改成「CRLF 归一化」的哈希：能过，但把平台细节写死进校验规则。
- 关闭/跳过该文件的哈希校验：等于放过资产漂移。

### 一个必须提醒 Lead 的副作用（已处理）

加 `*.svg -text` 后，**工作区里那份 2236 B 的 CRLF 文件会被 git 判定为「已修改」**——`-text` 让 git 不再做换行归一化，于是工作区字节 ≠ 索引字节。如果不处理，提交时会把 CRLF 版本写回仓库，把这次修复直接毁掉。

本轮已把该文件工作区字节刷成 LF（2236 → 2198 B），刷新后：

```
git hash-object --no-filters src/assets/avatars/psych-teacher-cartoon.svg  → a2cd298c6ba4cc397ae8a5bd4e9d24187e08f590
git rev-parse HEAD:src/assets/avatars/psych-teacher-cartoon.svg            → a2cd298c6ba4cc397ae8a5bd4e9d24187e08f590
git ls-files --eol → i/lf w/lf attr/-text
```

即工作区、索引、HEAD 三者 blob 完全一致，`git status` 里该文件已消失，**不需要重新提交这个文件**。

踩到的坑：刷新后 `git status` 仍报 M，原因是索引 stat 缓存里还记着 `size: 2236`，与实际 2198 不符。`git update-index --refresh` 和 `--really-refresh` 都刷不掉它，最后靠「touch 该文件 → `git update-index --refresh -- <file>`」修好，缓存 size 变 2198。**没做任何 `git add`**，`git diff --cached` 全程为空。

## 10. 生成器归一化（v1.2 追加）

上一版把 `scripts/build-design-assets.mjs` 的裸字节哈希留作遗留项。本轮已补齐，规则与 `check-assets.mjs` 的 `hashFile` 完全一致。

改动 3 处 + 1 条共用规则（`git diff` 为 `1 file changed, 11 insertions(+), 3 deletions(-)`）：

| 位置 | 原实现 | 现实现 | 作用 |
| --- | --- | --- | --- |
| 文件头 | — | 新增 `TEXT_ASSET` 与 `digestFor(relative, bytes)` | 单一规则出口，注释指明必须与 `check-assets.mjs` 的 `hashFile` 保持一致 |
| 第 37 行（`save`，写 approved 资产） | `createHash('sha256').update(data)` | `digestFor(relative, data)` | 按扩展名判定文本/二进制 |
| 第 151 行（上游 `sourceSha256` 校验） | `createHash('sha256').update(raw)` | `digestFor(input, raw)` | 与 `check-assets.mjs:179` 校验 `sourceSha256` 用的 `hashFile(inputPath)` 同口径 |
| 第 169 行（legacy 资产） | `createHash('sha256').update(data)` | `digestFor(relative, data)` | 同上 |

**关键取舍**：`digestFor` 按**扩展名**判定，`svg|txt|md|json|css|js|mjs` 归一化，其余（`png/webp/ico`）保持原始字节。这与校验侧 `TEXT_ASSET` 正则逐字相同，不是另写一套。

**上游 6 个 `.svg.txt` 的 pin 不受影响**：实测这 6 个文件全是纯 LF（`CR=0`），`git ls-files --eol` 显示 `attr/-text`，所以「原始字节哈希」与「归一化后哈希」本来就相等——`digestFor` 换上去前后，6 个 pin 全部照旧通过。这一条是本次实测确认的，不是推断。

### 一个被排除的误报
