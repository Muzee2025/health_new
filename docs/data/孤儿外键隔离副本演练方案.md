# 孤儿外键隔离副本演练方案

> owner：数据 ｜ version：0.1 ｜ status：方案草稿；未执行任何数据库操作 ｜ updated：2026-11-14

## 目标与边界

基于[数据治理现状与差距](数据治理现状与差距.md)中登记的聚合发现，设计 `psychological_reports` 到 `users` 的外键孤儿处置比较演练。目标是比较“保留现状”“在副本中模拟删除”“有可信归属证据时在副本中模拟改绑”三种结果，为业务责任人提供影响依据；本方案不决定真实记录的最终处置。

本方案只描述后续隔离副本演练，不读取或写入 `backend/health.db`，也不读取本机快照、行内容、`.env` 或运行日志。不启动应用服务，不运行迁移脚本或旧 `backend/scripts/init_db.py`。当前回合只检查了 Git 状态、治理文档、备份脚本和既有测试源码；没有连接 SQLite、运行测试或执行备份/恢复。

## 开始演练前的门槛

1. 由有权的数据责任人指定一份已批准、可用于本次演练的静态 SQLite 备份副本，并确认来源、生成时间、完整性和可处理范围。演练脚本的输入只能是这份副本；不得直接把 `backend/health.db` 或运行中的数据库路径作为源。
2. 若没有获批副本，演练只使用新建的合成 SQLite 夹具：复现父表/子表外键结构及一条孤儿关系，不引入任何真实业务行。此结果只证明处置逻辑，不代表真实数据库已恢复或已修复。
3. 在 Git 忽略且受访问控制的临时目录下，为本次运行新建唯一目录。每个输出路径必须事先不存在；不得复用失败残留、覆盖已有数据库或把含业务数据的副本放入版本库、交付目录或共享日志。
4. 固定演练输入和程序版本，先核对输入是常规文件、目标目录不是源目录，并在私有记录中保存来源摘要与副本摘要。对外记录仅留聚合状态，不记录行标识、账号标识、正文、风险值或可逆映射。

## 演练步骤

1. **建立不可变基线副本**：使用[现有备份/恢复工具](../../scripts/backup-restore-database.py)的 `backup` 操作，从获批的静态副本复制到一个全新目标路径。该工具以只读方式打开源、拒绝已有目标路径，并核对 `quick_check`、表数和外键违规总数；输出只保留聚合值。若输入无法获批或检查失败，停止，不进入处置演练。
2. **记录基线**：在基线副本上以只读连接记录 `integrity_check`、`quick_check`、`foreign_key_check` 违规总数、表/列结构摘要、各表行数摘要及目标表行数。预期基线为页面完整性通过、目标关系存在 1 条外键违规；如果实际计数不同，先暂停并由责任人复核，不按旧报告强行执行。
3. **冻结母本并分支**：基线副本只读保留，不直接执行任何处置。分别从基线复制生成独立的 `control`、`delete-simulation` 和 `relink-simulation` 文件；每份目标都用新路径。任何一步异常都不覆盖或复用原路径。
4. **运行控制组**：不改动 `control` 副本，只重复完整性、结构和聚合行数核对。它应与基线一致，并继续报告原有外键违规。
5. **运行删除模拟**：仅在 `delete-simulation` 副本中删除经私下核验的那条孤儿子记录。预期违规总数归零、`psychological_reports` 行数减少 1，其他表行数和 schema 不变。该分支只用于量化丢失记录的后果，不作为推荐修复。
6. **运行改绑模拟（条件执行）**：只有责任人提供可信业务来源证据并书面确认目标归属时，才在 `relink-simulation` 副本中把外键改到已核实的父记录。不得为了让检查变绿而选择任意现存用户或补造占位用户。没有证据时，将本分支记为“未执行：归属未确认”。成功分支预期违规总数归零、子表行数不变，其他字段与各表行数不变。
7. **复查与封存**：每个分支分别提交事务并关闭写连接，再重新以只读方式运行检查。记录每个分支的结果、退出码、程序版本和目录代号；不导出 SQL 行、截图或业务正文。保留演练副本和失败残留到责任人审阅完成，不做自动递归清理。

建议调用的工具形式如下。尖括号是操作员在隔离环境中的本地路径占位符，不可替换为正在运行的数据库路径；本方案未执行这些命令。

```powershell
.\.venv\Scripts\python.exe scripts/backup-restore-database.py backup `
  --source <获批的静态备份副本> `
  --destination <本轮全新隔离目录>/baseline.db

.\.venv\Scripts\python.exe scripts/backup-restore-database.py restore `
  --source <本轮隔离目录>/baseline.db `
  --destination <本轮隔离目录>/control.db
```

其余处置分支同样从 `baseline.db` 使用独立新目标路径建立。现有测试源码已覆盖合成 WAL 备份/恢复、孤儿保留、拒绝覆盖和拒绝符号链接；后续如需验证工具行为，应使用仓库既有隔离测试入口，不把测试通过等同于本次数据演练通过。

## 结果判定

| 分支 | 写入范围 | 预期外键违规数 | 预期业务影响 | 结论用途 |
| --- | --- | ---: | --- | --- |
| 基线 / 控制组 | 不写入 | 1（若实际基线不同则暂停） | 行数、schema 与基线一致 | 证明保留现状的检查结果 |
| 删除模拟 | 仅独立副本 | 0 | 报告表行数减少 1 | 量化记录损失；未获责任人决定前不建议采用 |
| 改绑模拟 | 仅独立副本，且先有可信归属证据 | 0 | 行数不变，归属关系改变 | 量化经证据支持的最小修复效果 |

所有分支的 `integrity_check` 必须为 `ok`，schema 必须与基线一致，预期外的表行数变化必须为 0；否则该分支判失败并停止。每份副本都应与基线隔离，处置分支不得反向修改基线。

## 推荐与决策边界

目前没有足以证明孤儿记录正确归属的业务证据。建议先保留原记录，控制组作为当前状态基线；删除和改绑仅作隔离副本中的条件性演练。工程检查通过不等于业务归属确认，也不构成删除、改绑、迁移或生产放行授权。任何真实数据库处置都需另行决策、授权和备份/恢复安排。

## 交付物与验收条件

- 方案审阅通过，指定获批输入来源、保管人和隔离目录。
- 基线及每个处置分支使用唯一新文件；原始库、运行服务和上传文件未写入。
- 私有机器记录保留完整性检查、外键违规总数、schema/行数摘要、命令退出码和运行版本；版本化报告只保留脱敏聚合结论。
- 删除分支仅改变目标报告行数；改绑分支只有在可信证据和书面批准后才运行；未批准的改绑明确标为未执行。
- 全部副本审阅完毕后再决定如何安全归档或清理本轮新生成的临时文件；不得触碰运行目录内原有数据。
