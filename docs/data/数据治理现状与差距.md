## 结论

当前代码模型、字段字典和本机登记库不是同一 schema 版本：字段字典的 198 个表—字段键与现行 ORM 模型完全对应；按团队记录核对的目标文件 backend/health.db 只有 21 张表、157 列，缺少现行模型中的 6 张表。该数据库 SQLite quick_check 为 ok，但 foreign_key_check 检出 1 条 psychological_reports 到 users 的外键孤儿。本轮未读取该行内容或输出其键值，也未更改数据库。

仓库具备 SQLite 新路径备份/恢复工具和合成数据恢复证据；本机存在数个较早的快照文件，但它们都留在同一仓库机器目录、schema 与目标库不完全相同，且不能证明异机副本或真库恢复演练已经完成。现有隐私流程和学生告知仍是待校内确认的草案。上线前的主要缺口是：确认运行服务实际绑定的库、在隔离副本评估 schema 迁移、完成独立备份与恢复演练、补齐校方隐私责任与数据生命周期。

本报告只记录现状与建议，不构成迁移、孤儿处置、专业评估或生产放行授权。

### 孤儿记录处理建议

保持原样，不删除、不改绑、不补造归属。团队既有记录也建议保留待决。若后续需要处理，先在新建隔离副本中生成脱敏核验摘要，再由有权的数据责任人基于可信业务证据确认归属和保留义务；业务决定和审批记录完成后，才讨论最小修复及复核条件。不得把“quick_check=ok”当成允许修复或迁移的依据。

### 迁移脚本风险与边界

仓库有独立的师生分配、求助工作流和唯一索引迁移工具。求助工作流脚本要求显式数据库路径与新备份路径，按事务新增表/触发器；唯一索引迁移会先备份并拒绝重复数据。prepare-local-database.py 只为新副本准备 schema，并明确不会补齐既有表的缺失列。以上脚本均不得直接对当前目标数据库执行，须先在全新隔离库或备份生成的新副本上演练。

迁移入口分散在 backend/migrations 与 backend/scripts，当前盘点未找到统一 schema 版本账本或覆盖所有环境的迁移状态登记。另有两项旧入口需要持续隔离：backend/scripts/init_db.py 含 Base.metadata.drop_all(bind=engine)；backend/scripts/migrations/20260411_drop_risk_level.sql 含 DROP COLUMN，且标注为 MySQL/PostgreSQL。两者都不应作为 SQLite 线上升级入口；本轮均未运行。

## 建议按以下顺序推进

1. **冻结真库写入计划**：先由项目责任人确认 backend/health.db 是否是实际运行库、环境归属和维护窗口；在确认前不执行迁移、不改孤儿、不用旧 init_db.py。
2. **在隔离副本做 schema 与迁移演练**：从经批准的只读源生成全新副本；按依赖顺序逐项检查 6 张缺表的迁移条件，记录表/列/索引差异、迁移前后聚合校验与外键违规基线。保留孤儿原状，不能把修复计入迁移成功条件。
3. **做独立备份与恢复演练**：先确定需保护的数据库、上传和生成文档卷；由校方确认备份目标、加密、权限、异机副本、频率、保留、RPO/RTO 与责任人。把副本恢复到另一个全新隔离路径，验证完整性、结构、批准的聚合不变量和应用可读性；演练全过程不得覆盖现有数据库或运行文件。
4. **把字典升级为治理目录**：保留现有 198 字段结构字典，以模型 schema 生成表/字段键；另补每类数据的责任人、业务目的/依据、来源/去向、敏感级别、访问角色、保留与删除规则、外部处理方、版本和审批状态。生成后对模型 schema 做差异检查。
5. **校内批准学生隐私流程**：确认数据处理主体与联系人、逐类收集必要性、告知/同意及未成年人处理规则、访问/导出审批、权利请求、AI外发、事故响应、人工承接和试点退出流程；更新告知文本并留审批记录。所有缺失的真实组织信息保持待填写，不由工程团队代填。
