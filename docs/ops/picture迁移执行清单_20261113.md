## 8. `npm run assets:build` 会覆盖 manifest（处置方案）

### 8.1 事实

`scripts/build-design-assets.mjs` 是**全量重建**脚本，不是增量同步：

- `:70` `const entries = []` —— 条目从空数组开始
- `:505-508` `await fs.writeFile(path.join(assetRoot, 'manifest.json'), JSON.stringify({ version: '2.0.0', updated: date, assets: entries }, null, 2) + '\n')` —— **整文件重写**，不做合并
- `:483-489` 的 legacy 遍历是**硬编码白名单**，只有 `psych-teacher-cartoon{,-48,-96,-192}` 和 `psych-teacher-{1,2,3}` 共 7 个，**不含** `legacy/` 下新移入的 3 个
- `:530` 同时重写 `LICENSES.md`，表体由 `:511-516` 对 **`entries` 全量** map 生成（不只 approved，非 approved 的行写「来源待核实 / unverified」）。实测佐证：当前 `LICENSES.md` 数据行 **131 行**，正好是迁移前的条目数，不含新增 3 条

所以前端手工补的 3 条会在重跑时丢失，`check-assets.mjs:384-388` 立刻报 3 条 `COVERAGE_MISSING`（error）→ `assets:check` FAIL。冰仔的判断属实，我在 HEAD `a7b6764` 上独立复核确认。

### 8.2 但不只是「丢 3 条」——实测还有两处偏差

假如直接把 3 个文件加进 `:483` 的白名单，生成结果**和前端的条目仍不一致**（实测 `tmp/probe-build-ids.cjs`、`tmp/probe-legacy-parity.cjs`）：

| 字段 | 白名单循环会生成 | manifest 现值（前端写的） |
| --- | --- | --- |
| `id` | `legacy-avatar-teacher-legacy-01-png` | `legacy-teacher-photo-01-png` |
| `source` | `仓库既有文件；原始来源与授权待核实` | `仓库既有文件 picture/22417447….png；原始来源与授权待核实` |

原因是 `:493` 的 `id` 由 `path.basename(relative)` 推导，`:499` 的 `source` 是固定字符串、记不住原 `picture/` 文件名。

好消息：**现有 7 条 legacy 条目与循环生成结果逐字段完全一致（7/7，0 处不符）**，说明这个循环就是权威生成器，只要 `id`/`source` 对齐，重跑 build 是幂等的、不会产生额外 diff。

### 8.3 方案对比

**方案①：改 `:483` 白名单，把 3 个新 PNG 加进去**

- 改动：`scripts/build-design-assets.mjs` 一处数组（3 行）；另需让 `id`/`source` 能表达原 `picture/` 来源，否则 manifest 会被改成上表左列，`docs/` 与 `manifest` 的 id 对不上（当前 id 仅被 `docs/ops/picture迁移执行清单_20261113.md` 和 `manifest.json` 自己引用，`git grep` 实测 0 处代码引用，所以改名不炸代码，但会让文档失真）
- 收益：重跑 build 幂等，`assets:build` 与 `assets:check` 自洽，长期正确
- 成本/风险：改 `scripts/` 归测试（与本清单第 4 节同一文件归属问题）；`id` 若要保留语义需额外引入「原路径」映射，脚本变复杂

**方案②：文档写明 `assets:build` 是重建脚本、手工条目会被覆盖（不改脚本）**

- 改动：只改文档（本节即该文档）
- 收益：零代码风险、零归属冲突，立刻可执行
- 风险：**残留隐患**——将来任何人跑一次 `assets:build` 就静默丢 3 条并 FAIL，且 `assets:build` 不在 CI 里（`.github/workflows/offline-quality.yml:42-44` 只跑 `assets:check`、`assets:source-test`、`assets:source-check`），所以 CI 抓不到，只有本地重跑才暴露

**我的建议：①（但拆成两步，降低风险）**

理由：方案②只是把坑写下来，坑还在；而 `assets:build` 是项目里唯一能重建素材库的入口，留一个「跑一下就破坏交付」的脚本不可接受。但①有 `id`/`source` 语义问题，所以：

1. **先加白名单**（3 行，`status: legacy-unverified` 由循环自动给），让「重跑不再丢文件」——这一步是止损，优先级高
2. `id`/`source` 的对齐单独评估：若接受 `id` 变成 `legacy-avatar-teacher-legacy-0N-png`，则①一次做完；若必须保留 `legacy-teacher-photo-0N-png`，则在循环里加一个可选的原路径映射（形如 `{ path, sourceNote }`），改动约 6 行

### 8.4 一个必须知道的前提：本机现在跑不了 `assets:build`

`scripts/build-design-assets.mjs:10-26` 启动时 `require('sharp')`，失败即抛错退出。实测：

```
node -e "require.resolve('sharp')"  →  MODULE_NOT_FOUND
Test-Path node_modules\sharp         →  ABSENT
SHARP_MODULE_PATH / NODE_PATH        →  未指向可用 sharp
```

`sharp` 不在 `package.json` 的 `dependencies`/`devDependencies` 里（`:10-26` 的注释明确写「No install is performed」）。**所以「跑一次 build 验证方案①是否幂等」这件事，在本机做不了**，除非用户提供 sharp 模块路径（`SHARP_MODULE_PATH`）。

这也解释了为什么这个坑一直没被发现：**没人跑得起来 build**。因此方案①的验证只能在有 sharp 的环境做；本机能做的只有静态核对（我已做：现有 7 条 7/7 一致）。

### 8.6 定案（2026-11-13，冰仔拍板）

**选方案①，`id` 允许对齐为生成值。** 即接受 `legacy-teacher-photo-0N-png` → `legacy-avatar-teacher-legacy-0N-png`。

但这带来一个必须同时处理的连带影响：**`source` 字段不能跟着塌成固定串**。

`:499` 的 `source: '仓库既有文件；原始来源与授权待核实'` 不含原路径。而这三张图的原路径是 `picture/22417447….png` 这类**哈希文件名**，是这批文件唯一的来源线索——`picture/` 目录已随迁移删除，一旦 `source` 被覆盖成固定串，`git log --follow` 之外就再也查不到原文件名了。这违反 `AGENTS.md:59`「归档旧材料必须保持内容可追溯并登记原路径」。

所以定案的改法是把 `:483` 的字符串数组改成「路径 + 可选 source」的对象数组，`:499` 改成 `it.source ?? '<原固定串>'`。

**已用探针预演过（`tmp/probe-plan1.cjs`），与当前 manifest 的字段差异只有 3 处 `id`，`source`/`sha256`/`size`/`status`/`license`/`owner`/`usage`/`type`/`path` 全部逐字段一致。** 也就是说改完后重跑 build 只会改 3 个 `id`，不会动其它任何字段。
