# 全栈 Docker 部署与 SQLite 恢复

> owner: D / Lead整合 ｜ version: 0.2 ｜ status: 配置通过静态核对 镜像拉取受网络阻塞 ｜ updated: 2026-10-22

## 范围与状态

本说明提供 Linux Docker Compose 的可复跑构建配置、离线 CI 和 SQLite 新路径备份/恢复命令。工作目录、Docker daemon 与持久卷均应是本项目新建的隔离环境。仓库原Windows本地服务使用5173/18080；Compose的HTTP端口4186只绑定loopback，后端仅容器网络可达。本轮没有启动、停止或连接其他项目容器。

Compose的HTTP/TLS配置已静态验证。Lead实际尝试构建backend-runtime，在读取Docker Hub的python:3.12-slim元数据时连接超时，退出1；镜像尚未生成，未运行容器或验证Nginx实际启动。没有签发真实证书、公网部署、完成负载评估或生产恢复演练。HTTP只供本机冒烟验证，配置成功不代表上线门禁通过。

Nginx镜像固定为`1.30.6-alpine`，2026-10-22核对[上游stable版本](https://nginx.org/en/download.html)及[Docker官方支持标签](https://hub.docker.com/_/nginx)。构建上下文白名单包含实际COPY所需的Nginx配置，排除运行库、上传与秘密配置。TLS配置保留loopback维护HTTP监听，且单独定义共享限流区；静态JS/CSS启用gzip，API禁用代理缓冲以保留流式响应。上述Nginx配置仍需在可拉取镜像的Linux环境执行`nginx -t`与实际流式/TLS验证。

## Linux 隔离准备

需要安装 Docker Engine 与 Compose plugin、Git、Python 3.10+、Node 24。选择校方批准的Linux主机、域名、数据目录、备份策略和运维责任人。先核对端口4186、443、容器网络以及主机磁盘配额没有冲突。首次操作在校方新建的空项目目录和独立 Compose project 下进行；不要导入原数据库、上传、`.env` 或历史运行目录。

检出代码后，在部署主机外部建立私密配置文件和证书目录。目录权限限定给部署账号，`.env`不进入仓库：

```bash
install -d -m 700 /opt/health-new/secrets /opt/health-new/tls
umask 077
cat > /opt/health-new/secrets/backend.env <<'EOF'
JWT_SECRET_KEY=在校方密码管理流程中生成至少32字节随机值
EOF
```

部署前将占位行替换为本部署新生成的随机值；不要把值写入shell历史、工单、聊天或CI。模型API密钥只有经过单独批准并完成提供商评估后才加入。未配置时保持模型能力不可用。不要复制其他环境的密钥。

项目位置示例为`/opt/health-new/app`，下列命令从仓库根目录运行。Compose project 使用新名称`healthnew-fullstack`：

```bash
cd /opt/health-new/app
export COMPOSE_PROJECT_NAME=healthnew-fullstack
export RUNTIME_ENV_FILE=/opt/health-new/secrets/backend.env
export PUBLIC_ORIGIN=http://127.0.0.1:4186
docker compose -f deploy/fullstack/docker-compose.yml config --quiet
docker compose -f deploy/fullstack/docker-compose.yml build
```

前端镜像只带`src/`、`public/`、入口/锁文件及共享图表的四个`docs/design`源文件；忽略文件由`deploy/fullstack/Dockerfile.dockerignore`控制。后端镜像只复制`backend/app`、依赖文件及白名单中的初始化、迁移、教师账号、师生分配和备份工具，不复制`.env`、数据库、上传、日志、生成文档或仓库其他源码。镜像构建会下载锁定npm依赖及requirements中声明的运行包，构建前应按校方变更流程审查依赖源和镜像版本。

## 新数据库与本机 HTTP 验证

容器默认SQLite单worker。部署卷分别保存数据库、用户上传、日志、生成文档、临时生成文件。数据库、文档和生成目录不由Nginx映射；文档下载继续经应用鉴权。现有后端仅有`public_images`与`teacher_avatars`两类图片静态路由，且限制图像MIME；这两类头像/公开素材仍可通过Nginx `/static/` 读取，不应上传敏感信息。Nginx限制上传请求体并按客户端IP限速/限连接，当前限速状态仅在单个Nginx实例共享，横向扩容须另做评审。没有配置公网入口或共享Redis限流。

SQLite volume 初次为空时，应用readiness会保持失败。只在确认这是新的空卷后，显式创建全部模型schema：

```bash
docker compose -f deploy/fullstack/docker-compose.yml run --rm --no-deps \
  --entrypoint python backend scripts/init-empty-database.py \
  --database /var/lib/health-new/database/health.db
```

该工具拒绝既存目标。该命令创建全新schema，不会迁移旧数据库，也不会分配师生关联。SQLite新建schema包含求助/跟进表及追加审核事件的保护触发器；其他数据库不据此宣称具有同等保护。

已有本项目数据库升级时，先停止本项目写入并完成独立恢复演练，再在批准的运行副本执行版本化增量迁移。以下命令只适用于独立副本，不得直接指向未备份的旧库；backup目标必须不存在：

```bash
docker compose -f deploy/fullstack/docker-compose.yml run --rm --no-deps \
  --entrypoint python backend scripts/migrate-support-workflow.py \
  --database /var/lib/health-new/database/health.db \
  --backup /var/lib/health-new/database/before-support-upgrade.db upgrade
```

迁移新增三张求助/跟进表、两张账号状态/操作事件表及追加保护触发器，拒绝不兼容的既有结构；已有兼容的求助三表可继续增量升级。不会为未知历史记录补归属、自动分配或创建教师账号。备份在私有卷内保留后还应转存到校方批准的独立备份介质。不要用空库初始化命令覆盖数据卷。运维工具通过明确白名单COPY入镜像，使用方法见[校内运营与隐私流程](校内运营与隐私流程.md)。

仅本机HTTP检查：

```bash
docker compose -f deploy/fullstack/docker-compose.yml up -d
curl --fail http://127.0.0.1:4186/api/health/ready
```

确认输出只标识服务与schema就绪后，再由部署负责人决定是否开放访问。该HTTP入口只绑定loopback；不要把4186直接映射公网。常用查看命令是`docker compose -f deploy/fullstack/docker-compose.yml logs --tail=100`与`docker compose -f deploy/fullstack/docker-compose.yml ps`。

## 正式 TLS 配置

正式入口要求校方批准的真实域名和证书。先通过校方证书流程在`/opt/health-new/tls`放置`fullchain.pem`与`privkey.pem`，并验证域名DNS/防火墙已指向主机。文档中的`health.example.edu`仅为占位，证书和DNS不会由本项目生成。设置真实域名的HTTPS origin并验证证书/私钥权限：

```bash
export PUBLIC_ORIGIN=https://health.example.edu
export TLS_CERT_DIR=/opt/health-new/tls
docker compose -f deploy/fullstack/docker-compose.yml \
  -f deploy/fullstack/docker-compose.tls.yml config --quiet
```

校方批准后用两个compose文件启动，TLS入口监听443；基础文件中的4186仍只绑定loopback供本机维护，不得暴露。必须通过校方边界网关、防火墙和TLS扫描验证，再发布DNS。不得将自签或占位证书报告为正式TLS。当前未实际验证Nginx TLS启动和证书续期。

## 备份与恢复演练

备份脚本只读打开源SQLite，用SQLite backup API生成一致性副本，包含WAL中已提交数据；源文件及源目录不被写入。备份和恢复都只允许写入一个全新目标。目标已存在、源为符号链接或目标目录不存在时拒绝执行。脚本检查源与目标`quick_check`、表数与`PRAGMA foreign_key_check`违规数。输出只包含检查结果和计数，不包含路径、连接串或行内容。

将数据库备份到权限受限且与主机分离的校方备份盘；文件名不能含学生身份：

```bash
umask 077
python scripts/backup-restore-database.py backup \
  --source /校方私有挂载/health.db \
  --destination /校方备份挂载/health-2026-10-22.db
```

恢复演练必须使用隔离临时目录中的备份副本和新的输出路径：

```bash
python scripts/backup-restore-database.py restore \
  --source /校方备份挂载/health-2026-10-22.db \
  --destination /校方隔离演练目录/restore-drill.db
```

脚本不会自动删除、补齐或重分配外键孤儿。`quick_check=ok`只表示SQLite内部页面快速一致性检查通过；它不表示外键完整。若`foreign_key_violations`非零，脚本报告“存在既有外键违规”并保留内容，业务负责人须先确认归属，再批准单独的数据修复。恢复文件是否可用于应用升级，还需核对schema版本、应用readiness和业务抽样；本轮没有读取或演练真实数据库。

本地合成回归命令：

```bash
python scripts/run-backend-baseline.py backend/tests/test_backup_restore_database.py
```

测试覆盖WAL写入、备份→新路径恢复→合成行校验、外键孤儿的保留/报告、拒绝覆盖与拒绝符号链接。
