# 历史重写方案（只出方案，不执行）

> owner: 资产 ｜ version: 1.0 ｜ status: 方案待批 ｜ updated: 2026-11-13
> 起点：`git status --short` 于 2026-11-13 01:06 记录，HEAD `60ee8e2`；测量期间 Lead 推到 `12fe934`，本文所有体积数字在 `12fe934` 上复测。

## 0. 一句话结论

**不建议重写历史。** 实测重写全部历史最多省 **15.0 MiB（99.43 → 84.46 MiB）**，代价是 84 个提交的 SHA 全变、19 个本地分支与 12 个 tag 全部作废、27 份文档里的提交号引用失效、所有协作者必须重新 clone。

而**真正能白拿的 24.1 MiB 不需要重写历史**：当前 `.git` 里 517 个松散对象 + 19 个 prune-packable 占 16.3 MiB，两个 pack 从未全量 repack。只跑一次 `git gc` 就能从 123.04 降到 98.68 MiB，零风险、零 SHA 变化。

**先做 `git gc`，重写历史这件事优先级应降到最低。**

## 1. 先更正我上一份报告的两个错误

上一份《方案A执行清单》和更早的《交付资产盘点》里，我把「history-only blob 24.6 MB」当成「重写历史能省的体积」。**这个换算错了**，原因是我拿未压缩的对象大小当成了磁盘占用。

### 1.1 错误一：24.6 MB 是未压缩字节，不是磁盘占用

用 `git verify-pack -v` 逐个对象读出真实 in-pack 字节数：

| 口径 | 对象数 | 字节 | 说明 |
| --- | --- | --- | --- |
| history-only blob **原始大小** | 879 | 26,379,496 B / **25.16 MiB** | 我上一份报的数字 |
| history-only blob **打包后** | 32 | 4,702,926 B / **4.49 MiB** | 真实占用 |

**差 5.6 倍。** 那 879 个「history-only」里绝大多数是 `platform-events.csv`（16.3 MB 原始）这类高度可压缩文本，以及同一文件的历史版本——它们和当前版本共享 delta，几乎不占额外空间。

其中单个最大项是 `deliverables/心域智链项目策划书_内容完善修订稿_20261029.docx` 的旧版本 `90a361ca`，打包后 4,559,705 B / **4.35 MiB**，占 history-only 总打包体积的 **97%**。**其余 31 个 history-only blob 加起来只有 143 KB。**

### 1.2 错误二：真正 24 MiB 的体积在松散对象，不在历史层

`git count-objects -v` 当前实测：

```
count: 517            ← 松散对象个数
size: 16661           ← 16661 KiB = 16.27 MiB 松散对象
in-pack: 3147
packs: 2
size-pack: 108982     ← 106.43 MiB
prune-packable: 19    ← 19 个已在 pack 里、本地还留着的重复松散对象
```

镜像克隆全量 repack 实测（`git clone --mirror` → `git repack -a -d -f` → `git gc --prune=now`）：

| 状态 | `.git` 体积 |
| --- | --- |
| 当前工作仓 | **123.04 MiB** |
| 镜像克隆原样 | 122.77 MiB |
| 全量 repack 后 | **98.67 MiB** |

**省 24.1 MiB，一个 SHA 都没变。** 这就是我上一份报告里「clone 不会缩小」那句话的正确答案——不是「必须重写历史才能缩小」，而是「必须全量 repack 才能缩小」。

### 1.2.1 决定性证据：回收松散对象靠 `git gc`，跟重写历史无关

`tmp/rw-repack-only` 这个探针**只做了 `git repack -a -d -f`，一次历史重写都没做**：

| 指标 | 源仓（未处理） | `rw-repack-only`（仅 repack，零重写） |
| --- | --- | --- |
| `count`（松散对象个数） | 517 | **23** |
| `size`（松散对象体积） | 16661 KiB / 16.27 MiB | **16 KiB** |
| 提交数 | 84 | 83（浅克隆时 HEAD 前移，非重写所致） |
| HEAD | `12fe934` | `f7fed84`（未重写，仍是原始 SHA） |

**517 → 23，16.27 MiB → 16 KiB，SHA 一个没变。**

松散对象是「曾经写过、后来被打包进 pack」的冗余副本，`git gc` 按「不可达 + 已被 pack 覆盖」两条规则就能清掉，**完全不需要动提交历史**。重写历史的作用是让 blob 变得不可达，那是另一回事。

所以「真正省体积的是重写历史时排除松散对象」这个因果关系**不成立**——省松散对象靠的是 `gc`，重写历史省的是「让大 blob 不可达」那部分（实测最多 15 MiB，见 §2）。

### 1.3 为什么 clone 一次实际只有 99.43 MiB，不是 101 MB

用单 pack 直接测传输量（`git pack-objects --stdout`，字节重定向，避开 PowerShell `>` 的 UTF-16 陷阱）：

| 内容 | 传输体积 |
| --- | --- |
| 全部 refs（84 提交 / 19 分支 / 12 tag） | **104,262,372 B = 99.43 MiB** |
| 仅 HEAD 树 | 104,189,149 B = 99.36 MiB |
| 仅 HEAD 树、且先精简掉 5 个大项 | 104,190,341 B = 99.36 MiB |

**后两行是关键证据**：把当前树里最大的 5 项（模拟库目录、模拟库 ZIP、逐页预览目录、两个大 CSV/PPTX）全部 `git rm --cached` 之后，clone 传输量**一点没变**（99.36 → 99.36 MiB）。因为那些 blob 仍然被祖先提交引用，`pack-objects` 照样要打包它们。

**推论：只要历史里存在过大文件，「移出跟踪」对 clone 体积零收益。** 这直接推翻了方案 A 里「工作树从 152 MiB 降到 134 MiB 就能改善 clone」的隐含假设——改善的是**工作树**，不是 **clone**。

## 2. 重写历史到底能省多少：三组实测

全部在 `git clone --mirror` 出来的副本上做，用 `git filter-branch --index-filter`，完成后 `update-ref -d` 清 `refs/original`、`reflog expire --expire=now --all`、`gc --prune=now`、`repack -a -d -f`，再用 `pack-objects` 测真实传输量。

| 探针 | 排除内容 | `.git` 体积 | clone 传输量 | 相对现状 |
| --- | --- | --- | --- | --- |
| 现状（全量 repack） | — | 98.67 MiB | **99.43 MiB** | — |
| `rw-junk` | 仅垃圾：`__pycache__`、`health.db`×2、`chroma_db`×3、`logs`、`coverage`、`.idea`、`.workbuddy`、`backend/temp` | 97.96 MiB | — | **−1.47 MiB** |
| `rw-big` | 仅大交付物：模拟库目录+ZIP、逐页预览目录 | 85.31 MiB | — | **−13.36 MiB** |
| `rw-all` | 垃圾 + 大交付物 + 6 个 ZIP | 84.60 MiB | **84.46 MiB** | **−14.97 MiB** |

### 2.1 三组数字怎么读

**垃圾清理几乎没用（−1.47 MiB）。** 92 个垃圾 blob 原始 4.00 MiB，其中 `backend/health.db` 一个就占 1.68 MiB——但 SQLite 文件压缩率极高，打包后整批只有不到 1.5 MiB。

**收益全在 `deliverables/` 那几个大交付物上（−13.36 MiB）。** 具体是：

| 路径 | in-pack 字节 | 说明 |
| --- | --- | --- |
| `deliverables/心域智链_高校两学期模拟库_20261104.zip` | 11,567,682（11.03 MiB） | 一个文件占 `rw-big` 全部收益（13.37 MiB）的 **82.5%** |
| `deliverables/逐页优化预览_20261101/…参考稿_20261101.pptx` | 6,452,082 | PPTX 是 zip 套 zip，压缩率极低 |
| `deliverables/心域智链_高校两学期模拟库_20261104/platform-events.csv` | 2,059,349 | 原始 16.3 MB，压缩到 2.06 MB |
| `deliverables/逐页优化预览_20261101/optimized/optimized.pdf` | 1,407,558 | 与顶层 PDF 同 sha256 |
| `deliverables/…/student-semesters.csv` | 367,756 | 原始 4.7 MB |

注意：这 5 项相加是 21.85 MiB，但重写只省 13.36 MiB——因为 `platform-events.csv`、`student-semesters.csv`、`optimized.pdf` 在历史里还有别的引用，删掉一个路径不等于删掉 blob。

**再加 6 个 ZIP 只多省 1.6 MiB（−13.36 → −14.97）。** 7 个 ZIP 里 5 个成员 100% 重复，压缩后本就高度共享 delta，删掉收益极小。

### 2.2 结论：重写历史的天花板是 15 MiB，不是 24 MiB

即使把所有垃圾和大交付物都从全部历史里抹掉，`clone` 也只能从 99.43 降到 84.46 MiB。**剩下的 84.46 MiB 里，`docs/` 占 23.40 MiB in-pack（788 个文件，证据链，不能动），其余是未移除的交付物与源码**——交付物是用户要拿去申报答辩的东西，动不了。

## 3. 重写历史的影响面（谁的在途分支会废掉）

### 3.1 当前仓库状态

| 项目 | 数量 | 明细 |
| --- | --- | --- |
| 提交总数 | **84** | 全部在 `codex/application-delivery` 上，无分叉 |
| 本地分支 | **19** | 全部已 merge 进 HEAD（`git branch --no-merged HEAD` 为空） |
| 远端分支 | 3 | `origin/master`、`origin/codex/application-delivery`、`origin/HEAD` |
| tag | **12** | 全部在本地，**远端一个都没有**（`git ls-remote --tags origin` 为空） |
| stash | 0 | — |
| worktree | 1 | 仅主仓 |
| 未合并分支 | **0** | `git branch --no-merged HEAD` 无输出 |
| 开放 PR | 0 | GitHub API 实测 |

**好消息**：没有未合并的在途分支，没有开放 PR，没有 stash。这意味着「重写会让别人的分支废掉」这个最常见风险**在当前仓库不存在**。

**坏消息**：19 个本地分支 + 12 个 tag 全部指向被重写的提交，重写后**全部失效**，必须逐个重建。`master` 是 2026-05-15 的老提交（`a7e6f5a`），也在重写范围内。

### 3.2 SHA 失效会打断什么

`git grep` 实测：**27 份 docs 里的 Markdown 引用了真实提交 SHA**。举三处原文：

- `docs/design/设计方案.md:5` — 「历史说明：本文件为初始W1方案，对应 `4b2898f`。」
- `docs/test/仓库基线.md` — 引用 `a7e6f5a`（root commit，即 `master` 头）
- `docs/ops/方案A执行清单_20261113.md` — 引用 `c134b07`

重写后这些引用**全部指向不存在的对象**。AGENTS.md 要求「归档旧材料必须保持内容可追溯并登记原路径」，SHA 失效等于追溯链断掉。

**这是重写历史最实质的代价，比体积收益重要。** 省 15 MiB 换 27 份文档的追溯链断裂，不划算。

### 3.3 还需要注意

- **`master` 是 2026-05-15 的旧提交**，与当前分支共同祖先在 5 月。重写会把整个 5 月至今的历史全部改写。
- **远端 tag 为空**，所以远端不需要删 tag；但本地 12 个 tag 要重建。
- **`.git` 里 241 条 reflog 记录**在重写时会被清空，本地回滚能力归零。
- **重写后必须强推**（`--force`），这会触发 GitHub 的 force-push 保护提示，且其他 clone 过的人必须 `git reset --hard` 或重新 clone。

## 4. 三套方案对比

### 方案 R0：只做全量 repack（推荐，立即执行）

```bash
# 在本地主仓执行，不涉及任何提交
git gc --prune=now
```

| 项 | 值 |
| --- | --- |
| 体积变化 | 123.04 → **98.68 MiB**（−24.36 MiB） |
| clone 传输量 | 99.43 MiB（不变） |
| SHA 变化 | **无** |
| 分支/tag 影响 | **无** |
| 文档引用 | **无影响** |
| 风险 | **极低**。`git gc` 只清理不可达对象，已被 19 个 prune-packable 和 517 个松散对象证实是垃圾 |
| 可逆性 | 不可逆（垃圾对象被删），但删的都是不可达对象，无信息损失 |
| 需要谁做 | Lead（Git 操作归 Lead） |

**这是唯一「白拿 24 MiB」的动作。** 建议优先做，做完再讨论其它。

补充：`git gc` 只影响本地。要让**别人 clone 也变小**，需要 `git repack -a -d -f` 后强推一次（pack 文件会重新生成并上传），或者等 GitHub 侧自动 GC。**GitHub 的仓库大小显示（101 MB）不会因为本地 `git gc` 而改变**——那需要重写历史或联系 GitHub Support 触发 GC。

### 方案 R1：清理历史垃圾（不推荐单独做）

用 `git filter-branch --index-filter` 从全部历史移除垃圾路径。

| 项 | 值 |
| --- | --- |
| 体积变化 | 98.68 → **97.96 MiB**（−0.72 MiB） |
| clone 传输量 | 约 −1.47 MiB |
| SHA 变化 | **84 个提交全变** |
| 分支/tag 影响 | 19 分支 + 12 tag 全部重建 |
| 文档引用 | 27 份文档的 SHA 引用失效 |
| 风险 | **高**。`filter-branch` 会重写全部提交；中途失败留下 `refs/original` 需要手工清 |
| 可逆性 | 差。必须事先 `git clone --mirror` 备份 |

**收益 0.72 MiB，代价是全库 SHA 重写。绝对值不值。**

### 方案 R2：重写历史移除大交付物（不推荐，作为备案）

| 项 | 值 |
| --- | --- |
| 体积变化 | 98.68 → **84.60 MiB**（−14.08 MiB） |
| clone 传输量 | 99.43 → **84.46 MiB**（−14.97 MiB） |
| SHA 变化 | 84 提交全变 |
| 分支/tag 影响 | 全部重建 |
| 文档引用 | 27 份失效 |
| 风险 | **高**。且**用户可能还要旧版交付物**——`deliverables/` 是申报答辩材料，历史版本正是「哪个是最新版」的证据链 |
| 可逆性 | 差 |

**能省 15 MiB，但把交付物的历史版本从库里抹掉。** 与 AGENTS.md 的追溯要求直接冲突。而且这 15 MiB 里的 11.57 MiB 全来自**一个文件**（模拟库 ZIP）——有更省事的替代：把这个 ZIP 挂到 GitHub Release 附件（见《方案A执行清单》§7 第 3 条），clone 立刻轻 11 MiB，且历史完整。

## 5. 如果一定要重写：标准步骤（含回滚）

**以下仅作备案，我不执行，由 Lead 与用户决定。** 前置条件：用户逐项批准 + 全部协作者暂停推送 + 已有可验证备份。

### 5.1 准备

```bash
# 1. 全量镜像备份（必须，且必须验证备份可用）
git clone --mirror https://github.com/Muzee2025/health_new.git ../health_new-backup.git
cd ../health_new-backup.git && git count-objects -vH && git rev-list --all --count
# 期望：84 个提交，体积与源仓一致

# 2. 记录重写前的所有 ref，用于事后核对
git -C ../health_new-muzee2025 for-each-ref --format='%(refname) %(objectname)' > refs-before.txt

# 3. 安装 git-filter-repo（比 filter-branch 快且安全）
pip install git-filter-repo
# 本机现状：Python 3.9.13 / pip 26.0.1，git_filter_repo 未安装（已验证 ModuleNotFoundError）
# git 2.54.0.windows.1 支持 filter-branch，但官方已弃用
```

### 5.2 执行（以 R2 为例）

```bash
cd ../health_new-backup.git
git filter-repo --force \
  --path 'deliverables/心域智链_高校两学期模拟库_20261104' --invert-paths \
  --path 'deliverables/心域智链_高校两学期模拟库_20261104.zip' --invert-paths \
  --path 'deliverables/逐页优化预览_20261101' --invert-paths

# 验证
git count-objects -vH
git rev-list --all --count          # 应仍为 84（未加 --prune-empty 时）
git for-each-ref --format='%(refname) %(objectname)' > refs-after.txt
diff refs-before.txt refs-after.txt  # 预期：全部 SHA 不同
```

### 5.3 推送（高风险，不可逆）

```bash
git push --force --all
git push --force --tags      # 远端本无 tag，此步会新建 12 个
```

### 5.4 回滚

**只能靠 5.1 的镜像备份。** 一旦强推且 GitHub 侧 GC 完成，原对象不可恢复。

```bash
# 从备份恢复
cd ../health_new-backup-original.git && git push --force --mirror
```

### 5.5 事后必须做

1. 逐个重建 19 个本地分支（备份仓里有完整 refs，可 `git branch <name> <new-sha>`）
2. 重建 12 个 tag（`refs-before.txt` 提供名字，SHA 需从新历史里找对应提交）
3. **更新 27 份文档里的 SHA 引用**——这是最容易漏的一步，且必须逐个确认新 SHA 对应同一个提交内容
4. 通知所有 clone 过的人重新 clone（不能 `git pull`，历史已分叉）
5. 更新 `docs/README.md` 索引与进度看板

**第 3 步的工时估计：27 份文档，每份要定位旧 SHA → 在新历史里找同一提交 → 替换。按每份 5 分钟算，约 2.5 小时，且需要逐条人工核对，不能脚本批量替换（SHA 是随机串，无法从内容反推）。**

## 6. 建议

### 6.1 立即做（零风险）

**方案 R0：`git gc --prune=now`。** 省 24.36 MiB，SHA 不变，分支 tag 不受影响。这是唯一「白拿」的动作，且当前 517 个松散对象 + 19 个 prune-packable 证明它确实有垃圾可清。

### 6.2 比 R2 更值的替代

**把模拟库 ZIP（11.57 MiB in-pack）挂到 GitHub Release 附件。** 效果：

| 项 | R2 重写历史 | Release 附件 |
| --- | --- | --- |
| clone 减少 | 14.97 MiB | 约 11.5 MiB |
| SHA 变化 | 84 提交全变 | **无** |
| 文档 SHA 引用 | 27 份失效 | **无影响** |
| 交付物历史 | **被抹掉** | 完整保留 |
| 可逆性 | 差 | **随时可撤** |

**用 Release 附件拿到 R2 的 77% 收益，代价是零。** 具体执行见《方案A执行清单》A1，那条我标了暂缓等归档位置定案——现在看应该升级为优先项。

### 6.3 不建议做

**方案 R1（清历史垃圾）**：省 0.72 MiB，代价是全库 SHA 重写。绝对不值。

**方案 R2（移除大交付物）**：省 15 MiB，代价是交付物历史被抹掉 + 27 份文档追溯链断裂 + 19 分支 12 tag 重建。**除非用户明确表示「旧版交付物不要了」，否则不做。**

### 6.4 优先级排序

1. **`git gc --prune=now`**（Lead 执行，零风险，−24.36 MiB）
2. **模拟库 ZIP 上 Release**（−11.5 MiB clone，零 SHA 变化）
3. 方案 A 的 A3–A8 六项（工作树 −7.03 MiB，改善本地磁盘与 `check-repo.py` 门禁）
4. ~~重写历史~~ **不做**

## 7. 测量方法与可复现命令

所有数字均可复现。**注意 PowerShell 5.1 的坑**：`>` 重定向会写 UTF-16 导致体积翻倍，测字节必须用 `cmd /c "... > file"`。

```bash
# 1. 当前体积
git count-objects -vH
(Get-ChildItem .git -Recurse -File -Force | Measure-Object Length -Sum).Sum / 1MB

# 2. 每个对象的真实 in-pack 大小（核心方法）
foreach($idx in (Get-ChildItem .git/objects/pack/*.idx)) {
  git verify-pack -v $idx.FullName
} | Where-Object { $_ -match '^[0-9a-f]{40} blob ' }

# 3. 真实 clone 传输量（字节重定向）
```

### A.4 我的建议
